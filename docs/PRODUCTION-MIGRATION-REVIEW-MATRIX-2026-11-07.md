## Cross-cutting findings

1. **The 26-file chain is a fresh-schema bootstrap allowlist, not a production upgrade plan.** The scripts explicitly refuse existing BTCBOX tables and the connected production project contains pre-existing state. Do not run bootstrap or Docker init against production or a persisted volume.
2. **Migration ledger mapping is unresolved.** The production ledger has timestamp versions that cannot safely be equated with four-digit source names. Do not infer applied/pending files from numeric sorting or timestamps.
3. **Order-sensitive intermediate contracts exist.** 0012 references fields/statuses added in 0022; 0026 public wrappers are intermediate and 0028 defines the final wrapper security state; withdrawal RPC evolves 9 → 10 → 11 arguments; Seconds RPCs are replaced across 0014/0024/0025. Test only the completed chain and record the effective final catalog.
4. **Constraint replacement is a data gate.** Before every DROP/ADD status, operation-type, duration, or policy constraint, capture distinct existing values and rows that would violate the replacement. Never use `DROP ... CASCADE` or mass-update unknown values to force success.
5. **Seed conflict semantics are intentionally non-overwriting in reviewed seeds.** The Earn catalog and initial Seconds policy use `ON CONFLICT DO NOTHING`; this preserves existing records but can leave them different from source defaults. Compare existing rows to approved expected values and decide explicitly whether drift is acceptable. Do not convert to `DO UPDATE` as an unreviewed “fix”.
6. **Security must be judged from final effective definitions.** Check every function's owner, SECURITY INVOKER/DEFINER, search_path, EXECUTE ACL, and any dynamic SQL. In particular, review the SECURITY DEFINER policy-read function in 0025 and all private/admin bridges after 0028; source-level grants in an earlier migration are not final-state evidence.
7. **Financial cutover is separate from schema installation.** No migration by itself authorizes enabling deposits, withdrawals, matching, Seconds orders, settlement, or manual credit. No production flags or balances may be changed during schema QA.

## Required staging preconditions and verification evidence

Before selecting any migration for an existing environment:

- Create a disposable isolated staging clone with a verified backup/restore point; never use the production connection string.
- Capture source SHA-256 manifest, full timestamp ledger, schema-only catalog report, and existing table/constraint/index/function/ACL inventory.
- Produce an explicit, owner-reviewed timestamp-to-source mapping. If evidence is insufficient, stop; do not guess.
- For every existing table, compare columns, types, defaults, constraints, indexes, RLS and grants. `IF NOT EXISTS` is not a schema reconciliation.
- Run the preflight for duplicate deposit TXIDs, earn product/asset mismatch, missing historical earn request hashes, duplicate request IDs, withdrawal status values, audit event IDs, Seconds duration/snapshot cohorts, and all constraints about to be replaced.
- Apply the full source chain to a fresh disposable database in the exact canonical order and separately rehearse the proposed data-preserving upgrade against a restored clone. Record before/after row counts and invariant checks; never use production data as a test fixture.
- Run PostgreSQL schema CI plus financial integration/concurrency/replay tests and final RPC catalog/ACL checks. Test no anon/authenticated direct table access, no browser EXECUTE, and no service-role direct private-table DML.
- Preserve reports, logs, exact source SHA, SQL checksums, approval record, rollback decision and recovery evidence.

### Minimum final-catalog checks

Run only on isolated staging after the full migration chain; adapt names only through reviewed SQL:

- List all overloads for `create_withdrawal_atomic`; require exactly one 11-argument identity.
- Verify all required public RPC signatures and role EXECUTE grants; require no PUBLIC/anon/authenticated EXECUTE on privileged functions.

- Verify final admin public wrappers are SECURITY INVOKER with empty search_path; inspect any SECURITY DEFINER function separately for fixed safe search_path and narrow grants.
- Verify audit append-only trigger, event_id uniqueness, withdrawal status constraint, Seconds policy snapshots, and financial account/ledger invariants.
- Confirm no data rows were deleted, no balances changed, and no legacy state was silently imported or discarded by schema installation.
